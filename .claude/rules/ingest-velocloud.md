# `rsim-ingest`, VeloCloud

The VeloCloud module is in `velocloud/`: an enterprise of an orchestrator is one store device, and each edge is the twin device `<store device>/edge/<edge logicalId>` (`velocloud::device_name`). `velocloud::read` reads the sections of `velocloud::SECTIONS` into an `Enterprise`: the segments, the hub clusters, the object groups, the BGP sessions, the overlay rows of the route table, and each edge with its HA facts, segments, interfaces, static routes, BGP neighbours, WAN links, gateways, hub references, SD-WAN peers, module state and effective firewall and business policy; `velocloud::Parsed` keeps each JSON value with its stanza, so each read value keeps its lines.

`velocloud/effective.rs` gives the effective body of a module of an edge: the module of the profile that the `configuration` scope of the listing row binds, with the `edgeSpecificData` of the edge on top; a segment block merges by segment, key by key, and in a rule list the edge rules come first, then each profile rule whose `ruleLogicalId` no edge rule repeats. With no `profiles` section, the profile part of each module is not known: a policy with edge rules keeps them and ends each rule list with an unknown tail, and a policy with none is not read. The listing rows of one link logicalId are one WAN link: the row with the `internalId` of a WAN module row, else the one row; with more than one row and no such row, the link is not known (`WanLink::ambiguous`). The kind of a link is the `mode` of its WAN module row, and a private carrier name gives a private link only for a link with no WAN module row.

`velocloud/rules.rs` reads the rules of the firewall and of the business policy into typed matches, with the address groups and port groups of `object_groups`; `appid`, `classid`, `hostname`, `os_version`, `dInterface`, `dvlan`, `smac`, `dmac`, each key that the reader does not map, a value that does not read and a group with a domain or with no record are bounds of the rule, and the route action keeps `routePolicy`, `linkPolicy`, `serviceGroup`, the WAN link and the DSCP tags as read, with the known values of `RoutePolicy` and `LinkPolicy`. `velocloud/routes.rs` gives one overlay row for each preferred edge exit of the route table, with the router, withheld and eligible exits counted, and `RouteClass`, the order of the routes of one prefix length, in which a static route with Preferred off is the last resort. `velocloud/coverage.rs` classifies the stanzas of each section by a path with `*` for each array element and the module name for each element of `modules`.

`velocloud/lower.rs` lowers each edge, an HA pair included, into one twin device. A LAN interface goes through `vrf/<segment>`, the session lookup `session/<segment>` and the firewall `firewall/<segment>`, an `AclMatch` of the outbound rules whose list ends with the unhandled rule `firewall default`, to the route lookup `route` with one table for each segment; with a stateful firewall, `bypass/<segment>` (`SessionBypass`) sends the packets of a session past the firewall, a route to a LAN interface goes through the session commit `commit/lan`, and each tunnel selection has the session commit `<selection>/commit` before it. The table of a segment has the connected networks, the static routes and the overlay rows of the other edges, with one winner for each prefix by `routes::order`; a pair of routes whose order is not known gives `Unknown` for the prefix, and the overlay rows of the edge itself are not read. In a segment with a BGP neighbour, the static routes, the overlay routes and the default route are `Unknown` with the reason `lan learned routes not collected`, and only the connected and the local routes give an answer. An overlay route to an edge of the same role, branch to branch or hub to hub, is `Unknown`, and so is a backhaul rule of a hub. An overlay route goes to `sdwan/select/<segment>/<far edge>`, after `<selection>/qos`, a `QosNotEvaluated` with the QoS values and the edge-to-edge DSCP tags of the business rules of the segment, when a rule has them; the default route goes to the business policy `policy/<segment>`, a `PolicyRoute` that sends the packets of each rule to its route action for internet traffic: `direct/<segment>` with the NAT Direct of the WAN interface (`snat`), the session commit, the next hop and `exit/<interface>`, an egress that leaves the twin, through the public WAN links that are up or the pinned link, and `Unknown` for a link whose state is not collected or a pinned link that is down; the gateways of the segment; or the first backhaul hub, at `sdwan/select/<segment>/<far edge>/backhaul`; a rule with a QoS action or a DSCP tag goes through a `QosNotEvaluated` first. A rule with a NAT action, a route policy other than direct, gateway or backhaul, or no route action for internet traffic is unhandled, and the rule list ends with the unhandled rule `business policy default`.

`OverlaySelect` has one tunnel for each pair of a WAN link of the edge and a WAN link of the far end, public with public and private with private of the same private network; a tunnel is down when a link of `edge_state` is down, up when the paths of the peer in `sdwan_peers` that are up are as many as the tunnels whose links are up, and else not collected, and with no `sdwan_peers` data of the edge each tunnel that is not down is not collected. The steering rules of a selection are the business rules of the segment with the route action of its traffic, edge-to-edge for an overlay route and edge-to-cloud for the business policy: the link policy `fixed` pins the packets to the WAN link of the rule, and with the steering mode not in the data a pinned link with no tunnel up gives `Unknown`; a rule with no route action for the traffic or with `auto` keeps each tunnel; another `linkPolicy` value keeps each tunnel, is in the name of its rule and gives a note. The backhaul hub of a cluster of more than one hub is the hub of `sdwan_peers` with a path; with no such data, `HubChoice` gives the action: `None` makes the packets unknown, `All` makes each hub a candidate and `One` takes the first hub. `VcmpEncap` goes to `nexthop/wan` and `out/<interface>`, which links to the transport network of the link, or to the device of the estate at the far end of a link of the join, with the MAC of that end as the destination MAC; such a WAN link is no member of its transport network, and its address there has an unknown host route.

`velocloud/join.rs` gives the summary of each edge for the join: its LAN and WAN interfaces with their entry functions `in/<interface>` and addresses, the VRF of a LAN address from a segment other than the Global Segment, the address of a WAN interface as evidence and the listing address that differs from it as a shared address, the gateway of each WAN link and each BGP neighbour of a segment on the LAN interface of its local address or its network as an `AddressPeer`, with the rows of its observed sessions in the state `ESTABLISHED`, which go into the provenance of the link, and the static gateways, the WAN gateways and the BGP neighbour addresses as its next hops. A LAN interface with a link of the join sends its packets to the far end and is no edge interface. A WAN link that the lowering leaves out, on a LAN interface or on the interface of another link, has a note and an unknown host route in its transport network.

A WAN interface goes through `wan/route` to `vcmp/decap`, which gives the packets of a segment to `overlay/session` and `route`, and the packets with no VCMP encapsulation to the inbound rules: the session lookup, `inbound/dnat` with the port forwarding and the 1:1 NAT, the commit and the Global Segment. A transport network is a twin device, `<store device>/transport/public` for the public links of an enterprise and `<store device>/transport/private/<network>` for each private network: an ingress and an egress for each WAN link, and a `TransportLookup` with a host route to each link address and to each gateway, whose egress leaves the twin. A function that no ingress reaches is left out.

`estate.rs` reads a `velocloud` store device as `Input::Velocloud`, finds its enterprise with `velocloud::enterprise_of`, gives the coverage of the stanzas of no single edge to the store device and the coverage of each edge (`velocloud::coverage::classify_part`) to the twin device of the edge, adds the summary of each edge before the join, and lowers the enterprise with `HubChoice::None` and the links of the join. The tests use the synthetic sections in `crates/rsim-ingest/tests/fixtures/velocloud/`; they have fake secrets.
