# `rsim-ingest`, VyOS

The VyOS handlers are in `vyos/config.rs`, the table in `vyos/table.rs`, the lowering in `vyos/lower.rs` and the vendor profile in `vyos/profile.rs`. Each handler records the stanzas that it reads, and `vyos::unread` lists each handled stanza that no handler read. A new handled path needs a handler that reads it. The tests use the synthetic config in `crates/rsim-ingest/tests/fixtures/vyos/`.

A route to a WireGuard interface goes to `wireguard/<interface>` (`WireguardEncap` in `rsim-functions/src/tunnel.rs`) in place of an egress: the peer is the peer with the longest allowed IP that contains the destination, an allowed IP of more than one peer is `Unknown` ("more than one WireGuard peer allows <prefix>"), and a destination that no allowed IP contains is dropped; a peer with no endpoint address and port is `Unknown`. The outer header is UDP from the listen port (unknown with no `port` line) to the endpoint, with DSCP 0, and its source is the one address of the family of the endpoint on the one interface of the route of the main table to the endpoint, else unknown. The encapsulated packets are packets of the router: they go to the route lookup of the main table, with the local zone as their source zone (unknown with zones and no local zone), through the zone policy, the source NAT and the next-hop resolution to the egress; a global output filter or `policy local-route` makes them `Unknown`. The outer flow has the session state `SessionMatch::Untracked`: it is new or established, by which end started it, so `FirewallPolicy` evaluates it both as new and with the action of the state policy for established (`established`), and the packets for which the two differ are `Unknown`. `DeviceDelivery` gives `Unknown` for an encapsulated packet ("WireGuard packet at <device>, decapsulation not modelled"), so an outer packet to a router of the twin does not deliver. Handshakes and keepalives are not modelled, and the keys are not read.

The session lookup `SessionLookup` applies `StateActions`, the action of each connection state: accept, drop, continue or unknown. The VyOS lowering takes them from `firewall global-options state-policy`, where a state with no action continues; with no action for established, the zone policy evaluates the packets of a session too, and a rule with `state` matches the connection state through its `ZoneScope`. The other vendors use the default, with which the packets of a session pass the policy.

`vyos/ospf_config.rs` reads `protocols ospf` and `protocols ospfv3` of the main VRF and of each `vrf name <name>` into `rsim_routing::ospf::config::RouterConfig` (`vyos::ospf_config::read(doc, file)`), with the process name `""` and the VRF `default` for the main VRF. The schema of each version in that file gives the handled lines, and `push_entries` adds them to the table. A line with no entry in the schema is unhandled and goes into `Process::unhandled`. `log-adjacency-changes` is known-irrelevant. A value that the reader cannot represent, such as `network non-broadcast`, also goes into `Process::unhandled`. A line in `Process::unhandled` is not in `Config::read`, and `vyos::unread` reports it. An OSPFv2 interface joins an area through `interface <name> area <a>` with each of its IPv4 addresses, or through each address that an `area <a> network <prefix>` line covers with a prefix length that is not longer than the length of the address. Network lines of 2 areas that cover one address are unhandled. `area 0` and `area 0.0.0.0` are one area. If 2 stanzas of one area have different `area-type` stanzas, both `area-type` stanzas are unhandled. An `area-type` stanza with 2 or more types is unhandled. Some interfaces get an address that the config does not hold. For OSPFv2, these are an `address dhcp` line, the `source-interface` line of a `pppoe` interface, an `sstpc` interface and the `mode client` line of an `openvpn` interface. For OSPFv3, these are an `address dhcpv6` line, an `ipv6 address autoconf` line, a `dhcpv6-options pd <n> interface <name>` line of an interface that is not disabled, and the `mode client` line of an `openvpn` interface. Such an OSPFv2 line of an interface that is not disabled is unhandled in each OSPFv2 process of its VRF with a network line. If an `interface <name> area <a>` line or an `area <a> interface <name>` line names the interface, the interface joins the area. Then the line of the address is unhandled if the interface is not disabled. An OSPFv3 interface joins through `interface <name> area <a>` or `area <a> interface <name>`, with its first IPv6 address that is not link-local. A second line that puts the interface in a different area is unhandled. The address, the VRF, the admin state and the default network type come from `interfaces`: loopback for `loopback`, point-to-point for `pppoe`, `sstpc`, `wireguard`, an `openvpn` interface with no `device-type tap` and a tunnel with a remote address that is not a GRE TAP tunnel, and broadcast for each other interface. A `vti` interface is an xfrm interface, and its network type is broadcast. This is not confirmed on a device. The `bandwidth` line is in Mb/s, and an interface with no `bandwidth` line has no bandwidth.

## Commands

| Task | Command |
|---|---|
| Coverage of a VyOS config | `cargo run -p rsim-ingest --example vyos_coverage < config.json` |
| Twin of a VyOS device of a store | `cargo run -p rsim-ingest --example vyos_snapshot -- <data folder> <device>`. Add `<ingress interface> <source> <destination> tcp\|udp <port>` for a path query. |
