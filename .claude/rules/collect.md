# `rsim-collect`

`rsim-collect` is the only crate that talks to devices. It runs a collection cycle as stages with bounded channels: schedule, fetch, classify and hash, extract, and store.

Each `Device` has its interval (`DEFAULT_INTERVAL` 60 s; from the inventory, the resolved `interval_seconds`; from an env file, 60 s). The scheduler (`schedule.rs`) takes the due time of a device from its last collection and its current interval, or from the backoff after a failure, and a device is due when its due time is at most the slack of 1 s after the cycle time; a collection is forced at the first collection after the full interval of 900 s, and each time for a device whose interval is 900 s or more. The collector wakes at the earliest due time of the devices of the inventory (`Collector::next_wake`), at once for a device to remove, and at most `WAKE_LIMIT` (60 s) later, so it reads the inventory again; a cycle with no due device and no removal writes nothing.

The SSH transport is in `ssh.rs`, the HTTPS transport in `https.rs`, and the credentials and the pins of host keys and certificates in `trust.rs`. `path.rs` holds the route of a device: the proxy and the jump hosts. The address of a device or a jump host is a host, `host:port`, or a URL of the scheme of its transport (`https://` or `ssh://`) with no user and no path, which `trust::plain_address` reduces to the address for the connection and the pin. `tunnel.rs` logs in to each hop of a route, and both transports use it.

The HTTPS transport checks a certificate against a pin, a CA bundle, the public roots of `webpki-roots` (`TlsTrust::PublicRoots`) or not at all, sends a `Secret::Token` as `Authorization: Token <secret>` with no login, gets a token for a `Secret::OAuthClient` with the client credentials grant at `OAUTH_TOKEN_PATH` and sends it as `Authorization: Bearer <token>`, logs in again once after a 401 for a password and an OAuth client, and has `get`, `get_status` and `post_read`, a POST of a JSON body to a path of the fixed read list of the source; `get_status` and `post_read` give a status from 400 to 599 to the source as `HttpReply::Status` with at most 200 characters of the body on one line, and after a 429 they hold each request to the address for the wait of `Retry-After` (seconds or an HTTP date, else 5 s) and try again while the device has retries (`HttpsLimits::retries`, default 0). The devices of one `ApiServer` address share its connection limit, which is its concurrency, its pace of that many request starts in each second, and its wait after a 429, and each jump host on the route to it needs a pinned host key; each request has the time limit `HttpsLimits::request_timeout` of 60 s, or the request time of its device (`HttpsTransport::with_request_timeout`).

`cli.rs` holds the text rules of a command line: the cleanup of terminal bytes, the prompt, the banner and the rejection lines of a vendor. The SSH transport has 3 command modes: `exec`, `shell` and `connection`. `../rsim-project/design/vendors.md` gives the rules. The features `ssh` and `https` turn on the transports, and `vyos`, `unifi`, `nxos`, `iosxr`, `iosxe`, `velocloud` and `equinix` turn on the sources.

An Equinix account (`Vendor::Equinix`) is one device `equinix-<name>` whose credential is an OAuth2 client: the env keys `<P>_CLIENT_ID` and `<P>_CLIENT_SECRET`, or a managed `password` credential with the client id as its user; its section time is the paged section time of the inventory. The Equinix source is in `equinix.rs`: it reads in order the sections `ports` (`GET /fabric/v4/ports`), `connections` (the search `POST /fabric/v4/connections/search` with the port uuids of `ports` of the same cycle, no read and an empty list with no port), and with the setting `network_edge` on, `edge_devices`, `edge_links` and `edge_connections` (the search with the device uuids of `edge_devices`), each the items of all pages with the offset paging of HST (`page_size`, default 100, at most 10,000 pages), redacted by `redact.rs`, sorted by `uuid` and then by the canonical bytes, with a keep list for each section but `edge_connections`. A section after a failed read that it waits for is failed with `not sent`; a 404 of the 2 Network Edge lists makes them absent, a 401 or 403 is `not authorized`, each other status fails the section with the body, and a connect error, such as a failed login, fails each section that is not read yet and stops the reads.

`redact.rs` holds the secret rule that the VeloCloud and Equinix sources share.

The VeloCloud source is in `velocloud.rs`: one device is one enterprise of an orchestrator, `vco-<orchestrator>-<enterprise logicalId>` with the logicalId in the field `site`, from the env keys `VELOCLOUD_<NAME>_*` or a device of the vendor `velocloud` in the inventory, whose `api-key` credential is the token (`Secret::Token`), whose resolved TLS trust, retries and request time go to the transport, and whose orchestrator settings give its `Orchestrator`; a device with no release fails before any read. It reads the sections `aggregates` (`getAggregates`, one read for each orchestrator in each cycle, kept until `Source::begin_cycle` of the next cycle), `edges` and `edge_state` (one `getEnterpriseEdges` answer, the configuration with the state fields volatile and the state by a keep list), `profiles`, `route_table` (a keep list of the route and exit fields), `edges_v2` (the paged API v2 edges, read only when `edges` gives a gap or no edge, else absent with `not needed`), `edge_modules` (`getEdgeConfigurationModules` for each edge with a numeric id: one object by edge logicalId, each module object or gap with the volatile `_freshness`), `sdwan_peers` (`getEdgeSDWANPeers` for each edge with a numeric id in each cycle), `bgp_sessions` (the paged API v2 sessions with `state[is]=ESTABLISHED` on page 1), `bgp_peer_status` and `object_groups`, in this order, with the Portal POST paths of `velocloud::READ_PATHS` only. A numeric id is a positive integer or a whole float. A Portal status 400, 403, 404, 405 or 501, a 200 answer with an `error` member, and for `bgpSessions` 403, 404, 405 or 501, is a gap: the section is absent with the operation and the status or the message as its reason; an enterprise with no numeric id has its Portal sections absent with `no numeric id for enterprise`. Each other status, an answer that is not JSON, a paging error and a release before 5.0.0.0 fail each section of the device, so the device keeps its last snapshot. A page token goes back as the only query parameter, and a `metaData` that is not an object, a token that is not a string, a repeated token or more than 10,000 pages fail the read.

`VelocloudMemory`, which the sources of all cycles share and which the binary fills at the start from the newest stored `edge_modules`, holds the modules of each edge under a memory key, a BLAKE3 hash of the orchestrator address, the base, the release, the enterprise and the identity of the token (`velocloud::token_id`), which `_freshness.key` stores; a fetch drops each held module of another key, so a new token or a new release reads each module again: an edge is read again only when the BLAKE3 signature of its serial number, the identity fields of its links and its `configuration` block changes, when its modules are older than the refresh ceiling (1800 s, 0 for each cycle), or when it has none; a transport error, a 429 or a 5xx keeps the held module with `stale: true` and its first time if the signature is the same, else gives the gap `Observation refresh failed`; a 401 fails the device; a gap is never held; a cycle with no failure drops the modules of the edges that it did not see. The requests of the enterprise devices of one orchestrator run on its workers, as many as its concurrency.

The secrets (the keys of the HST `SECRET_KEYS`, the keys with a word of `SECRET_WORDS` or `activationKey`, an SNMP community and a `{name, value}` setting record) get the value `[redacted]` before the hash and the store. The extracts give the tables `velocloud_edge_state`, `velocloud_link_state`, `velocloud_route` and `velocloud_bgp_session`. The commands `discover <name>` and `probe <name>` of the binary read the orchestrator `VELOCLOUD_<NAME>_URL` of the env file: the enterprises of the paged `GET <base>/enterprises`, and `GET <base>/enterprises/{id}/edges?limit=1` for each enterprise. `tests/velocloud.rs` runs the source on a fake orchestrator of `FakeTransport`, whose `reply_status` gives a status and whose `log` lists the calls.

The IOS XR source in `iosxr.rs` and the IOS XE source in `iosxe.rs` keep each answer as text; the ages, counters, uptimes and timers are volatile line shapes and word shapes.

The IOS XE source reads the MAC table (`mac_table`), the spanning tree (`spanning_tree`), `show vlan brief` (`vlans`), `show standby` (`hsrp_detail`) and `show vrrp` (`vrrp_detail`); `show ip arp` gives the ARP table of the global routing table, and the section `arp_vrfs` gives the ARP table of each VRF: after the other sections, the fetch reads the VRF names from the answer of `show vrf detail` of the same cycle and sends `show ip arp vrf <name>` for each VRF in name order, and the section holds a line `VRF: <name>` before each answer, or the line `VRF: <name> failed` for a failed command. With no answer of the VRFs, `arp_vrfs` is absent, except after a connect error or a timeout of the VRFs or of each command of the VRFs, which `arp_vrfs` takes as its error, so the section keeps its last blob.

The NX-OS source is in `nxos.rs`: the JSON answers get one shape, with each `ROW_x` as a list, and a keep list of a section names the fields that the change hash covers. The sections of the VXLAN tunnels, the EVPN MAC routes and the multicast routing have JSON keys that are not confirmed on a device, so they use volatile patterns for their times in place of a keep list.

The BGP setting of a router is the field `capture_bgp` of its `Device` (`CaptureBgp`), which `rsim-collect` reads from the env keys `<P>_CAPTURE_BGP` and `<P>_<NAME>_CAPTURE_BGP`: `sessions` reads the session summaries, `all` also reads the neighbour detail (`bgp_neighbors`) and the 3 tables of each IPv4 neighbour of the session answers of the same cycle (`bgp_routes`), and `off` reads no BGP section. `bgp.rs` holds the BGP parts that the sources share. Each BGP section is optional. On VyOS, a BGP answer whose first line starts with `%`, such as the answer of a router with no BGP instance, makes the section absent, and an empty answer is `{}`; an NX-OS switch with no BGP refuses both forms of the sessions, so `bgp_sessions` and `bgp_sessions_default` are absent. IOS XR and IOS XE store the answer of a router with no BGP, a line that starts with `%`, as a fresh section, and `bgp_vrf_sessions` and `bgp_routes` are then fresh and empty; the session reader of `rsim-ingest` takes a summary of only such lines as `NotCaptured`.

VyOS reads `show bgp vrf all summary json` (`bgp_sessions`) with a keep list of the AS, the router ID and the state of each neighbour; NX-OS reads `show bgp sessions vrf all | json` (`bgp_sessions`) with volatile patterns for its times and counters, and only when the switch refuses that form `show bgp sessions | json` (`bgp_sessions_default`), which is else absent; IOS XR reads `show bgp summary` and IOS XE `show ip bgp summary` (`bgp_sessions`), and both read the summary of each VRF of the `router bgp` block of the running config of the same cycle in name order (`bgp_vrf_sessions`, with a line `VRF: <name>` before each answer); each number and age of a Cisco summary is a volatile word, so the change hash covers the addresses and the state words.

With `all`, IOS XR reads `show bgp neighbors` (`bgp_neighbors`) and `show bgp vrf all neighbors` (`bgp_vrf_neighbors`), IOS XE `show bgp all neighbors` (`bgp_neighbors`), VyOS `show ip bgp vrf all neighbors json` and NX-OS `show bgp vrf all neighbors | json` (`bgp_neighbors`). `bgp_routes` holds a line `NEIGHBOR: <vrf> <address> <direction>` before each Cisco answer, or a JSON object of VRF, address and direction for VyOS and NX-OS; after 2 timeouts in a row, the route commands that are not sent are failed. On VyOS and NX-OS, a session answer that is not JSON makes `bgp_routes` absent, and NX-OS takes the neighbours from the first of `bgp_sessions` and `bgp_sessions_default` whose answer is JSON. A listen range is never a neighbour of a command. The BGP commands are not confirmed on a device, except the VyOS summary and tables on one router.

`ospf.rs` holds the OSPF sections that each source reads after its other sections, all optional: for OSPFv2 `ospf`, `ospf_interfaces`, `ospf_neighbors` and the database sections `ospf_lsdb_router`, `_network`, `_summary`, `_asbr_summary`, `_external` and `_nssa_external`, and for OSPFv3 `ospfv3`, `ospfv3_interfaces`, `ospfv3_neighbors` and `ospfv3_lsdb_router`, `_network`, `_inter_area_prefix`, `_inter_area_router`, `_external`, `_nssa`, `_link` and `_intra_area_prefix`. NX-OS reads `show ip ospf ... vrf all | json` and `show ospfv3 ... vrf all | json`, IOS-XE `show ip ospf ...` and `show ipv6 ospf ...`, IOS-XR `show ospf ...` and `show ospfv3 ...` of the default VRF, and VyOS the FRR `show ip ospf [vrf <vrf>] ... json` of each VRF with `protocols ospf` in the config of the same cycle, as one JSON object by VRF, and `show ipv6 ospf6 ... json` when the main table has `protocols ospfv3`. The age, the sequence number and the checksum of each LSA and the timers and counters of the process, interface and neighbour answers are volatile, so a refresh of an LSA gives no new snapshot. The OSPF commands are not confirmed on a device. `tests/ospf.rs` runs them on the fixtures of `rsim-ingest/tests/fixtures/ospf/`.

`https` needs `ssh`, because a console can be behind jump hosts. The pipeline tests use the fake transport in `fake.rs` and the synthetic fixtures in `crates/rsim-collect/tests/fixtures/`.

`demo.rs` holds the seed of a new store from a demo folder: `devices.txt`, with a line `<id> <vendor> <address> [<capture_bgp>]` for each device, where a line with no BGP setting reads the sessions, and a folder `cycle-<n>` for each cycle with a folder for each device, whose `commands.txt` maps each command to its reply file; a cycle holds only the files that differ from the cycle before it. The seed runs one cycle of the collector on the fake transport for each cycle, one hour apart from 2026-11-02 08:00 UTC, and a failed section is an error. The generator of `demo/` is the example `demo_enterprise`: one model of the devices, links and hosts (`build.rs`), the route tables from the shortest paths over the routing adjacencies and the VXLAN tunnels, the ARP and MAC tables and the spanning tree (`route.rs`), the OSPF database of area 0 of each OSPF router with its OSPFv2 sections (`ospf.rs`), the 3 tables of each BGP neighbour from the route tables (`bgp.rs`), and one renderer for each vendor. Each device with BGP has the BGP setting `all`. The accepted and the received table of a neighbour hold the BGP routes of the device whose next hop is the neighbour, and the advertised table holds the BGP routes of the far end whose next hop is the device. The AS path of a route has the AS of each eBGP hop toward its originating device. The provider of each internet edge sends the default route and 192.0.2.0/24, and the import policy of the edge permits only the default route. The prefix count of an IOS XR and an IOS XE session summary is the number of prefixes of the accepted table.

The fixtures use only documentation addresses and documentation MAC addresses. The transport tests in `tests/ssh.rs` and `tests/https.rs` run the real transports against servers on 127.0.0.1 in the test process. `tests/support/route.rs` holds the test jump host, which logs each login attempt, and the HTTP CONNECT and SOCKS5 test proxies. The test keys and certificates are made at test time. Do not commit private keys. The scheduler tests and the cycle tests use paused `tokio` time.

## Commands

| Task | Command |
|---|---|
| Collection tests | `cargo test -p rsim-collect` |
| NX-OS collection tests | `cargo test -p rsim-collect --test nxos` |
| IOS XR collection tests | `cargo test -p rsim-collect --test iosxr` |
| IOS XE collection tests | `cargo test -p rsim-collect --test iosxe` |
| VeloCloud collection tests | `cargo test -p rsim-collect --test velocloud` |
| Equinix collection tests | `cargo test -p rsim-collect --test equinix` |
| OSPF collection tests | `cargo test -p rsim-collect --test ospf` |
| BGP collection tests | `cargo test -p rsim-collect --test bgp` |
| One collection cycle of real devices | `cargo run -p rsim-collect --bin rsim-collect -- --env <env file> --data <data folder> run`. Add `--inventory <postgres URL>`, or set `RSIM_INVENTORY_URL` in the environment or in the env file, to read the devices from the inventory database at the start of each cycle; the env file is then optional and gives the secrets of the credentials of the source `env` or `env-url`, and the env key `RSIM_SECRET_KEY`, in the environment or in the env file, gives the key that opens the secrets of the managed credentials. Add `--repeat` for a cycle at each due time of a device, at least each 60 s. The `status` command shows the sections of the newest snapshot, and `show <device> <section>` writes the raw bytes of a section. The env file and the data folder stay outside the repository. The time limits are 45 s for a device and 20 s for a section; the env keys `<P>_TIMEOUT` and `<P>_SECTION_TIMEOUT` set them for a vendor, and `<P>_<NAME>_TIMEOUT` and `<P>_<NAME>_SECTION_TIMEOUT` for a device, in whole seconds. The env keys `<P>_CAPTURE_BGP` for a vendor and `<P>_<NAME>_CAPTURE_BGP` for a router set the BGP sections: `sessions` (the default), `all` or `off`. |
| SSH transport tests | `cargo test -p rsim-collect --test ssh` |
| HTTPS transport tests | `cargo test -p rsim-collect --test https` |
| Collection benchmark | `cargo bench -p rsim-collect --bench cycle` |
| Store of the demo estate | `cargo run -p rsim-collect --bin rsim-collect -- --data <data folder> seed --demo demo` writes the cycles of `demo/` into a new store through the fake transport, with no network; a store with a snapshot is an error, and with `--if-empty` the seed writes nothing and succeeds, as an init container needs. The image `rsim-collect` holds the folder in `/usr/share/rsim/demo`. |
