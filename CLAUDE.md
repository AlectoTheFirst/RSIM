## UI text: no AI prose

This rule has no exception. It applies to each text that a person reads in the product: a label, a button, a column head, a section head, a placeholder, a hint, a note, a `title`, an `aria-label`, an option of a select, a problem title and detail of the UI or of the API, and the reason text of the engine. Section 7.1 "Forbidden prose" of `../rsim-project/design/ui-design-language.md` is the full rule.

- A label names a thing or a state in a few words: "not known", "no reply", "secret key", "empty inherits from core". A button names its action: "Add credential", "Delete core-01".
- A label, a hint or a note is not a sentence. No full stop at the end of a label, and no explanation that a person did not ask for. A description goes only in the `title` of an element, in one short phrase.
- A section head has no note that explains the section, its rules or its security.
- Sentence case, present tense.

| Forbidden pattern | Examples |
|---|---|
| Sentences and explanations | "A jump host never gets the device credential.", "RSIM keeps the reference. The secret stays in its source.", "A managed secret is written once and never shown." |
| Conjectures and hedges | might, may, likely, probably, seems, appears to, it looks like, should work |
| Comparisons | instead of, rather than, unlike, better than, more than before, no longer, now as a comparison |
| Filler and intensifiers | simply, just, easily, actually, really, basically, quickly, fully, truly |
| Hype words and Claudisms | seamless, powerful, robust, comprehensive, intuitive, effortless, leverage, unlock, empower, elevate, streamline, delve, dive into, explore, journey, landscape, realm, crucial, key (as an adjective), ensure, game-changer, cutting-edge, next-level |
| Talk to the user | you, your, you can, feel free to, let's, we, please, don't worry, great, oops, sorry |
| Narration | Here is, Below you will find, This view shows, Note that, Keep in mind, It is worth noting |
| Summaries | In short, Overall, In summary, All in all |
| Rhetorical forms | a question in a label, "Not only ... but also", "It's not X, it's Y", groups of 3 adjectives |
| Decoration | emoji, glyphs such as `·`, `→`, `✓` and `•`, an em dash, an ellipsis as style, an exclamation mark, quotation marks for emphasis |

Before a UI change is done, read each new or changed text of the change against this table.

## Disk space

- Build in the shared folder `target` of this repository. For a build of a worktree or another checkout, set `CARGO_TARGET_DIR` to that folder.
- Do not make a separate target folder for a worktree, a branch, a benchmark or a check.
- Do not copy the source tree to make a build. Use a worktree.
- When the work of a worktree, a scratch folder or a source copy is done, delete it.
- Before a full build, a benchmark or a release build, do a check of the free space with `df -h`. If less than 20 GB is free, stop and tell the owner.
- If the folder `target/debug/incremental` is more than 20 GB, delete it.

The hand-built topologies are in the crate `rsim-topologies`, with one module for each topology in `crates/rsim-topologies/src/`. They are test fixtures with the twin identifier `builtin.<topology>`: a command of `rsim-cli` with such a name needs `--features test-fixtures`. `layer2_site()` is a switched site behind a router for the layer 2 tests; it is not a built-in topology. The tests and the benchmarks of `rsim-engine` use it as a development dependency. `scale_estate(ScaleOpts)` in `rsim-topologies/src/scale.rs` is the generated estate of the scale benchmark, from a fixed pseudo-random sequence; it is not a built-in topology. `rsim-topologies::builtin(name)` gives the twin of a hand-built topology.

`leaf_spine()` is a VXLAN fabric of 4 leaves and 2 spines with symmetric routing in one tenant VRF; `rsim-functions/src/tunnel.rs` holds its tunnel ends `VxlanEncap` and `VxlanDecap`.

`rsim-contract` has no engine dependency. It holds the JSON output types, the query echo and error types, the typed arguments of the operations, the brief forms `summary` and `steps`, and the registry of operations in `registry.rs`; `rsim-mcp` makes its tools and their schemas from the registry. `rsim-cli` converts the engine values with the trait `json::FromEngine`. `rsim-contract/src/table.rs` holds the table catalog, the selection parameters and the output types of a table request. `rsim-cli/src/frame.rs` holds the rows of a table as columns: each column is an Arrow dictionary array, one `u32` key for each row over the distinct values, and the rows are in key order. The selection works on the columns: a filter is evaluated once for each distinct value, a scan runs in chunks on `rayon`, a sort orders row numbers by the ranks of the distinct values with the row number as the last key, a page with no sort stops its scan at the end of the page, and JSON is made only for the rows of the answer; `crates/rsim-cli/src/frame/tests.rs` compares it with a selection on rows of JSON values. `rsim-cli/src/tables.rs` fills the columns of each table from a loaded twin once, when a request first names the table, and keeps them in `Loaded::tables`; the MCP tools `list_tables` and `table_query` and the REST API use them. The table `bgp-sessions` has one row for each BGP peer fact of a store twin, from `Loaded::bgp`. The table `neighbours` has one row for each LLDP or CDP record of a store twin that names a neighbour with no device in the twin, from `Loaded::seen` (`links::SeenNeighbour`): no device has its name or its host name and its MACs name no device, and the protocol is the section `lldp` or `cdp` of its span. The table `devices` has one row for each device with a function and each device of `Loaded::facts`: the vendor, the platform, the OS version, the serial, the management address and the time of the device manifest, each fact null with its column `<fact>_reason` (`not_collected` or `not_read`) when it is not known, the device of the store whose manifest gives the facts (`store_device`: the console of a UniFi device), and the spans of the facts; a hand-built topology of the tests has each fact `not_collected`. In the UI, the opened row of the table `devices` has the button "View functions", which opens the table `functions` filtered to the device, and a cell that the twin does not know has a hatch square and the words "not known" with the reason as its title. A claim answer has the field `detail` for what the claim leaves out of its rows. The BGP claims `bgp-peers-up` and `bgp-peers-agree` read `Loaded::bgp` with the far end of each neighbour from the join; a neighbour with `shutdown` gives no row in either claim, a neighbour whose peer is outside the twin gives no row in `bgp-peers-agree`, the detail counts them, and a scope with no row has the detail `no BGP neighbour in scope`. `bgp-peers-up` has one row for each configured neighbour and each dynamic peer of a listen range, a peer outside the twin included: established is confirmed, another state word is refuted, and a neighbour with no session row is refuted with `not in session table` only when the session section is `Complete` or `CompleteEmpty` and its scope covers the VRF and each activated address family of the neighbour; else it is unknown, as is a neighbour whose inheritance gap can hide a shutdown line and a neighbour named by its interface. `bgp-peers-agree` has one row for each configured neighbour whose peer address is an address of another device: a far side with no neighbour and no listen range for the source address refutes (`one-sided peering`) when the BGP config of the far device is read in full (`Summary::bgp_read`, which also counts the BGP stanzas that collected route rows make known-irrelevant), the neighbour of the far side for the source address refutes (`source address mismatch`) when it sends from a known address other than the peer address of the near side and gives unknown when its source address is not known, a neighbour of the far side that names another address of the near device refutes (`source address mismatch`) only when the far config is read in full, the far side has no session with the source address and no other neighbour of the near device can be its far side, an AS of the peer that is not an AS that the other side presents refutes in each direction (`asn mismatch`), and 2 sides with no common address family refute when both sets are known in full, with no inheritance gap and no address family that the reader does not name; a neighbour whose inheritance gap can hide its update-source has no known source address, and a gap that can hide a shutdown line turns each refute of its row into unknown; an AS or a source address that does not resolve, different session states and a count of sent prefixes that differs from the count of received prefixes of the far side with no inbound policy give unknown, never refuted. The scope of a query is the devices of the functions on its paths. `rsim-contract/src/claim.rs` holds the claim catalog and the rule of the result: one refuted row refutes, one unknown row makes it unknown, and no row is unknown; `rsim-cli/src/claims.rs` gives the evidence rows of each claim, and data that is not collected is unknown. `commands::load` gives a `Loaded` twin with its identity `twin::TwinJson`, and each top-level answer has the field `twin`: `builtin.<topology>` or `snap-<cycle>`, with an empty list of what-if layers. `crates/rsim-cli/tests/schema.rs` checks each stored answer against the schema of its kind and through a round trip, and the flags of `rsim path` and `rsim set` against the registry. `../rsim-project/design/http-api.md` is the API specification.

The prefix table in `rsim-core/src/prefix_table.rs` is a path-compressed trie with a read-only walk; `PacketSet::partition_by_prefix` and `PacketSet::partition_by_group` use the walk. `rsim-functions/src/fib.rs` holds the forwarding table `Fib`: the trie, the interned next-hop groups, compact spans and the protocol of each learned route as a column of its entry. A learned route (`RouteKind::Learned` with its `RouteProtocol`) shares the group of a static route with the same next hops, and the `fib` table and the step text name its protocol, for example `bgp`. `RouteLookup` splits a packet set by next-hop group, so a set query gives one branch for each forwarding result. `crates/rsim-core/tests/prefix_oracle.rs` compares the trie and both partitions with a brute-force longest-prefix match. `../rsim-project/design/rib-fib.md` gives the design.

`rsim-core` keeps the packet sets in `packet_set.rs`, the bit table in `bits.rs`, the arenas in `set.rs` and the description of a set as members in `describe.rs`. `crates/rsim-core/tests/explicit_oracle.rs` compares each set operation with an explicit list of packet pairs. Each header bit has 4 levels: the original request, the current header, the work level and the inner level. A frame has 0, 1 or 2 VLAN tags, each with its VLAN, its priority and its TPID: the outer tag `network.vlan.id`, `l2_priority` and `network.vlan.tpid`, and the inner tag `network.inner.vlan.id`, `inner_l2_priority` and `network.inner.vlan.tpid`; the bits of the 2 tags alternate, an inner tag needs an outer tag (`PacketSet::has_valid_tags`), `push_vlan` and `pop_vlan` move the outer tag to the inner tag and back, and `set_vlan(None)` removes both tags. In each setting of `unstated`, an inner tag that the query does not state is absent and a TPID that it does not state is `0x8100`; with `defaults`, a stated inner tag gives the outer TPID `0x88a8`. The JSON shows a TPID only when it is not `0x8100` and an inner tag only when it is present, and the query echo has the tag fields only when the query gives them. A layer 2 function gives `Unknown` for a frame with an inner tag. The encapsulation kinds are GRE, VXLAN, MPLS and WireGuard. A packet has at most one encapsulation: `PacketSet::encapsulate` moves the current header to the inner level and puts the outer header in the current fields, and `PacketSet::decapsulate` brings it back. The inner level is free for a packet with no encapsulation, and `PacketSet::has_free_levels` checks this in the tests. An outer header states each field. The JSON shows the inner header as `inner` of the current header. A path query runs on the set of its packet; the design note gives the rule for an unstated field. The ingress of a query comes from `--ingress` or from the attachment records and edge interfaces of the twin.

The OxiDD oracle in `crates/rsim-dd/tests/oracle.rs` compares the results with OxiDD on 3,256 levels. OxiDD is a development dependency only.

`rsim-api` is the REST server: `handler.rs` turns one request into one response with no socket, so the tests call it directly; `server.rs` is the HTTP/1.1 layer on `hyper` and `tokio`, with the engine work on worker threads and a limit of parallel queries; `openapi.rs` makes the OpenAPI 3.1 document from its route table and the schemas of `rsim-contract`, and `crates/rsim-api/openapi.json` is the committed copy that a test compares. A query is a resource: `POST /v1/twins/{twin}/queries` gives 303 to `/v1/twins/{twin}/queries/{qid}`, where `qid` holds the canonical query text, or its hash for a long query. Errors are problem objects of RFC 9457. The server gives the response of `GET .../queries/{qid}` the header `Server-Timing`: `engine;dur=<ms>` with the time of the handler, or `cache;desc=hit` for 304; the body stays the same bytes. `GET /v1/twins/{twin}/sources?file=..&lines=a-b` gives the masked source lines of a span (`rsim-cli/src/sources.rs`): the file `<device>/<section>@<blob>` is a section of the snapshot of the twin, read through the store of `Loaded`, and the lines are those of its canonical form with the secrets masked by `rsim_ingest::mask::section_lines`, numbered as the spans of the section number them: a JSON section and a running config by the lines of the stanza reader, and an IOS-XR or IOS-XE text section of `SECTIONS`, which a template of `rsim-textfsm` reads, by `rsim_textfsm::split_lines` (the line breaks of Python `splitlines`), which also numbers its records, its time line and the parts of `arp_vrfs`; a hand-built topology of the tests gives `no_source_text`, a section inside a span of text with no mask for its vendor and format gives `not_masked`, and a row span gives `no_source_text`. A row span (`SourceSpan::row`, `SourceSpan::is_row`) names the rows of a collected table, such as a UniFi device or client, a VyOS address row or an NX-OS JSON row, with the file `<device>/<table>@<blob>#row` and the row numbers from 1 as its lines; the step resource refuses its lines and the UI shows it as a label `<table> row <n>`. The span gate runs before the section is read and gives only the lines that lie inside a source span of text of a function of the twin, whatever the length of the section, and no answer names the line count of a section; a line of a span past the end of the section is not given: `sources::SpanIndex` holds the sorted, merged line ranges of all spans of text of each file, with no row span, from `NetFunction::each_span` (the provenance and the spans of the rules, routes, neighbours, hosts, MAC entries and links that a branch can name), built once for each loaded twin; the status depends only on the index: a range with no such line gives `not_a_source_span` (403), and a range with such a line gives 200 with the covered lines inside the section, and each other line of the range, outside every span or past the end of the section, in `left_out`, with a note; a range whose covered lines all lie past the end gives 200 with no lines. `crates/rsim-cli/tests/span_index.rs` checks that each span of text of each trace step lies inside the index and that a row span admits no line. `rsim-cli/src/topology.rs` gives the topology of a twin and the drawing of the paths of an answer, with the overlay edge of a tunnel and its underlay hops; `GET /v1/twins/{twin}/topology` and `GET .../queries/{qid}/topology` serve them. `rsim-mcp` is a library and a binary: `rsim-api` serves its tools at `/mcp`, and the twins of the tools share one cache, so parallel requests do not wait for each other. In `rsim-api`, the twin `store` is the newest built snapshot of the store (`Tools::reload_store`): a request for the store, a `snap-<cycle>` of the store or `GET /v1/twins` reads `HEAD`, and if it is newer than the current twin and no build runs, the twin of that snapshot builds on its own thread (`rsim-reload`, `commands::load_store_at`) while the current twin answers each request with no wait; when it is built, it becomes the current twin and the older one becomes the previous twin. Before a build starts, the server releases the previous twin, so it holds at most 2 twins. The first build runs in the first request for the store, and the other requests wait for it. A snapshot that does not build keeps the current twin, gives its error on stderr and in `reload_error`, and is not built again; a `HEAD` that cannot be read gives `reload_error` with the snapshot null. The current twin and the previous twin answer for their own `snap-<cycle>`; an older cycle gives 410 with the code `snapshot_replaced`, and a newer cycle that is not built gives 404. `POST /v1/twins/store/queries` gives the 303 to the query resource on the current snapshot with no 307 before it. The entry `store` of `GET /v1/twins` has `held` (the current twin), `previous`, `newest_cycle`, `loading` and `reload_error`. The UI pins a page to a run: a page on `store` moves to the `snap-<cycle>` of `held`, a new run does not change the page, the UI reads the twin list each 60 s and shows the button "Load latest run" when `held` is newer than the run of the page, and on `snapshot_replaced` (`onReplaced` of `client.ts`) the page moves to the newest built run with a note; the hatch mark beside the twin selector shows `reload_error`, and a request of a replaced run is sent again on `store` except a trace step and source lines (`onNewestRun`). `../rsim-project/design/twin-reload.md` gives the options of the reload and the plan of the delta twin. The brief forms come from the engine answer with no description of the packet sets of the trace steps (`json::brief_json`), so they cost much less than the full form. With no inventory database, the server has no sign-in and accepts only a loopback listen address. The server accepts the `Host` of its address and of each `--public-origin`, and the origins of `--allow-origin` and `--public-origin`; the probes `GET /healthz` and `GET /readyz` give no data and accept each host. `rsim-api/src/auth.rs` holds the sign-in: with the inventory database, `auth::gate` gives the rule of each route (open: the UI files, the probes, `/v1/auth/login` and `/v1/auth/setup`; a signed-in user: `/v1/auth/me` and `/v1/auth/logout`; a browser session: `/v1/auth/tokens`; else a scope: `rsim.admin` for `/v1/admin`, `rsim.inventory.write` for a PUT or DELETE of `/v1/inventory`, `rsim.read` for each other route, `/mcp` included), and the OpenAPI document takes the security of each operation from the same function. A request proves its user by the session cookie (`__Host-rsim_session` on HTTPS through a trusted proxy, `rsim_session` on plain HTTP; `HttpOnly`, `SameSite=Strict`) or by `Authorization: Bearer rsim_<64 hex digits>`; a request with a cookie that is not a GET or HEAD needs an `Origin` header. A token has the scopes that it names and that the role of its user gives. A refused request with credentials gets an event in `auth_events`. Each session and token has a limit of the request rate in memory (`auth::Rate`) with 429 and `Retry-After`. `POST /v1/auth/setup` makes the first admin only while no user exists, with no protection.

`rsim-inventory` holds the inventory in PostgreSQL through `tokio-postgres`, with TLS through `rustls` and `ring` and the CA bundle of `RSIM_INVENTORY_CA_FILE`. The schema is the SQL files in `migrations/`, which `Db::migrate` applies in order under an advisory lock and records in `schema_migrations`; a reader or a writer refuses a database at another schema version. The tables are the credentials (`credentials`: a name and the source `env` or `env-url` with its key, or the source `managed` with its kind `password`, `ssh-key` or `api-key`, its user, its secret sealed by ChaCha20-Poly1305 with the name and the kind as the associated data, the id of the key and the revision of the secret; `secret.rs` holds `SecretKey`, `SecretInput` and `Sealed`, `Db::load` gives no secret and only `Db::load_with_secrets` of the collector reads the sealed bytes), the jump hosts, the routes with their proxy URL with no login, the reference of the proxy login and the jump hosts in order (`route_jumps`), the device groups (the vendor and the settings), the devices (the name of the store, the address, the site, the location, the site of a console and the settings that override the group), the Equinix bindings (`fabric_port_bindings` and `edge_device_bindings`), `inventory_version`, `audit_log`, and the sign-in tables of `migrations/0002_auth.sql`: `users` (the role `viewer`, `operator` or `admin` and the Argon2id password hash), `sessions` and `api_tokens` (the SHA-256 hash of the token only), `login_failures` and `auth_events`. `db/auth.rs` holds their reader and writer: a session stops 12 hours after its last use and 7 days after the sign-in, 5 failed sign-ins of one user name or one client address in 15 minutes give a wait, the database gives each time, and the last enabled admin cannot lose the role or be disabled or removed. A setting of a device that is null inherits from its group, and a setting of a group that is null takes the default of `resolve.rs`: the credential, the route (none is a direct connection, and a route with no proxy and no jump host is a direct route that a device can set to override its group), the SSH algorithms, mode and channels, the NX-OS JSON form, the TLS trust and CA file, `capture_bgp`, the 4 time limits, the retries with 0 as the default and the HA setting `none`, `all` or `one` with `none` as the default; each resolved setting has its origin `device`, `group` or `default`. The collector does not use the retries, the HA setting, the request time and the time of a paged section yet. The vendor of a group is a word, and a vendor with no collector is allowed. `Db::apply` writes a list of changes in one transaction: a change that leaves its record as it is writes nothing, and otherwise the version increases by 1 and each changed record gets an audit record with the actor, the time of the database, the version, the kind, the key and the old and the new value. `env.rs` reads the env file of the collector (`parse_env`) and imports it (`import`): one group for each vendor with the reference `env:<P>`, the route of the vendor keys, a route of the device for a device with its own `VIA` or `PROXY` key, and the reference `env-url:<key>` for the login of a proxy URL. The binary `rsim-inventory` runs the migrations, the import and a print. In `rsim-collect`, `setup_from_inventory` of the binary turns the inventory and the secrets of the env file into the setup of a cycle, and its test checks that an env file and its import give the same devices, routes, credentials, profiles and time limits. `Collector::reconfigure` sets the inventory, the sources and the time limits before a cycle, and `Inventory::version` gives the version that the snapshot records. A failed read of the inventory, a reference with no secret and an inventory with no device of a collector write no snapshot, so a typing error does not remove devices. `rsim-api/src/inventory.rs` holds the routes `/v1/inventory`: `GET /v1/inventory/vendors`, the vendors of `rsim_inventory::COLLECTOR_VENDORS` with their transport, which needs no database and which a test of `rsim-collect` compares with `Vendor::ALL`, the GET routes of the inventory, the groups, the devices with the settings resolved, the credentials, the routes, the jump hosts, the bindings and the audit log, and the PUT and DELETE routes, which write with the actor `rsim-api`. Their OpenAPI scope is `rsim.inventory.write`. The SQL tests use a new schema for each test, from `rsim_inventory::test_database`.

`rsim-store` holds the format of the snapshot store, the writer and the reader. It has no network code. A device manifest records the host name or the address to which the collector connected (`management_address`), which an older manifest does not have. A snapshot manifest lists the devices that the snapshot removes and the version of the inventory database that the cycle read (`inventory_version`), which a cycle with no inventory database leaves out; the reader leaves a removed device out of that snapshot and the snapshots after it until a later snapshot lists the device again, and a checkpoint leaves it out. Each cycle of the collector removes each device of the newest snapshot that is not in the inventory, and the scheduler then takes a device that comes back as new. `rsim-collect` is the only crate that talks to devices. It runs a collection cycle as stages with bounded channels: schedule, fetch, classify and hash, extract, and store. The SSH transport is in `ssh.rs`, the HTTPS transport in `https.rs`, and the credentials and the pins of host keys and certificates in `trust.rs`. `path.rs` holds the route of a device: the proxy and the jump hosts. `tunnel.rs` logs in to each hop of a route, and both transports use it. `cli.rs` holds the text rules of a command line: the cleanup of terminal bytes, the prompt, the banner and the rejection lines of a vendor. The SSH transport has 3 command modes: `exec`, `shell` and `connection`. `../rsim-project/design/vendors.md` gives the rules. The features `ssh` and `https` turn on the transports, and `vyos`, `unifi`, `nxos`, `iosxr` and `iosxe` turn on the sources. The IOS XR source in `iosxr.rs` and the IOS XE source in `iosxe.rs` keep each answer as text; the ages, counters, uptimes and timers are volatile line shapes and word shapes. The IOS XE source reads the MAC table (`mac_table`), the spanning tree (`spanning_tree`), `show vlan brief` (`vlans`), `show standby` (`hsrp_detail`) and `show vrrp` (`vrrp_detail`); `show ip arp` gives the ARP table of the global routing table, and the section `arp_vrfs` gives the ARP table of each VRF: after the other sections, the fetch reads the VRF names from the answer of `show vrf detail` of the same cycle and sends `show ip arp vrf <name>` for each VRF in name order, and the section holds a line `VRF: <name>` before each answer, or the line `VRF: <name> failed` for a failed command. With no answer of the VRFs, `arp_vrfs` is absent, except after a connect error or a timeout of the VRFs or of each command of the VRFs, which `arp_vrfs` takes as its error, so the section keeps its last blob. The NX-OS source is in `nxos.rs`: the JSON answers get one shape, with each `ROW_x` as a list, and a keep list of a section names the fields that the change hash covers. The sections of the VXLAN tunnels, the EVPN MAC routes and the multicast routing have JSON keys that are not confirmed on a device, so they use volatile patterns for their times in place of a keep list. The BGP setting of a router is the field `capture_bgp` of its `Device` (`CaptureBgp`), which `rsim-collect` reads from the env keys `<P>_CAPTURE_BGP` and `<P>_<NAME>_CAPTURE_BGP`: `sessions` reads the session summaries, `all` also reads the neighbour detail (`bgp_neighbors`) and the 3 tables of each IPv4 neighbour of the session answers of the same cycle (`bgp_routes`), and `off` reads no BGP section. `bgp.rs` holds the BGP parts that the sources share. Each BGP section is optional. On VyOS, a BGP answer whose first line starts with `%`, such as the answer of a router with no BGP instance, makes the section absent, and an empty answer is `{}`; an NX-OS switch with no BGP refuses both forms of the sessions, so `bgp_sessions` and `bgp_sessions_default` are absent. IOS XR and IOS XE store the answer of a router with no BGP, a line that starts with `%`, as a fresh section, and `bgp_vrf_sessions` and `bgp_routes` are then fresh and empty; the session reader of `rsim-ingest` takes a summary of only such lines as `NotCaptured`. VyOS reads `show bgp vrf all summary json` (`bgp_sessions`) with a keep list of the AS, the router ID and the state of each neighbour; NX-OS reads `show bgp sessions vrf all | json` (`bgp_sessions`) with volatile patterns for its times and counters, and only when the switch refuses that form `show bgp sessions | json` (`bgp_sessions_default`), which is else absent; IOS XR reads `show bgp summary` and IOS XE `show ip bgp summary` (`bgp_sessions`), and both read the summary of each VRF of the `router bgp` block of the running config of the same cycle in name order (`bgp_vrf_sessions`, with a line `VRF: <name>` before each answer); each number and age of a Cisco summary is a volatile word, so the change hash covers the addresses and the state words. With `all`, IOS XR reads `show bgp neighbors` (`bgp_neighbors`) and `show bgp vrf all neighbors` (`bgp_vrf_neighbors`), IOS XE `show bgp all neighbors` (`bgp_neighbors`), VyOS `show ip bgp vrf all neighbors json` and NX-OS `show bgp vrf all neighbors | json` (`bgp_neighbors`). `bgp_routes` holds a line `NEIGHBOR: <vrf> <address> <direction>` before each Cisco answer, or a JSON object of VRF, address and direction for VyOS and NX-OS; after 2 timeouts in a row, the route commands that are not sent are failed. On VyOS and NX-OS, a session answer that is not JSON makes `bgp_routes` absent, and NX-OS takes the neighbours from the first of `bgp_sessions` and `bgp_sessions_default` whose answer is JSON. A listen range is never a neighbour of a command. The BGP commands are not confirmed on a device, except the VyOS summary and tables on one router. `https` needs `ssh`, because a console can be behind jump hosts. The pipeline tests use the fake transport in `fake.rs` and the synthetic fixtures in `crates/rsim-collect/tests/fixtures/`. The fixtures use only documentation addresses and documentation MAC addresses. The transport tests in `tests/ssh.rs` and `tests/https.rs` run the real transports against servers on 127.0.0.1 in the test process. `tests/support/route.rs` holds the test jump host, which logs each login attempt, and the HTTP CONNECT and SOCKS5 test proxies. The test keys and certificates are made at test time. Do not commit private keys. The scheduler tests and the cycle tests use paused `tokio` time.

## What the project is

The project is a Rust engine for a network digital twin. The engine compiles configs and collected state into typed network functions that stay in memory. The engine converges the routing internally. To answer reachability questions and policy questions, the engine sends packets or packet sets through the functions. Each answer has a full trace.

The scale target is 10,000+ routers and 50,000+ endpoints.

Section 3 of the brief shows the data flow and the crate layout. The project name is `rsim`, and each crate has the `rsim-` prefix.

## Rules that constrain all code

Section 2 of the brief gives 5 principles. Each principle changes how you write code.

| Principle | Effect on code |
|---|---|
| No confident wrong answers | Return `Unknown` with a reason when the engine cannot be sure. `Unknown` is a valid result. Do not report it as an error. |
| Deterministic | Do not use clocks or randomness. Do not let a result depend on the iteration order of an unordered collection. |
| Provenance everywhere | Each function instance keeps the source spans from which it came. A source span is a file and a line range. |
| Vendor behaviour is data | Put vendor defaults, tie-breakers and implicit rules in vendor behaviour profiles. Do not put them in engine code. |
| Functions written for simulation | Do not add packet buffers, checksums, queues, timers or I/O. |

## Function contract

Section 5 of the brief defines the contract for each function type. The `NetFunction` trait and the `Branch` struct in that section are illustrations. The implementer selects the final form. These invariants are not optional:

- A function accepts a `PacketSet` and returns one or more branches. The branches partition the input. No packet is lost and no packet is duplicated. At a forwarding choice, this rule applies in each alternative. At a flood, it applies in each copy.
- A function declares the context attributes that it needs and the context attributes that it supplies. The compile step of the twin validates the composition. A violation is a build error for that twin.
- A function declares the objects that it reads. These declarations control delta recompilation.
- A function declares the QoS header fields that it reads and writes. The context attribute declarations cover the QoS attributes. Refer to section 16.
- `FlowState` goes into a function and comes out of a function as a value. Do not hide session state or NAT state in a function.
- If part of a function came from an unhandled config stanza, the function returns `Unknown` for the affected packets. If only the match set of a predicate is incompletely known, use the match bounds in item 7 of section 5.

The delay, the alternative of a forwarding choice and the rate condition are part of the core types from step 1. Delay is virtual time. A function does not sleep. An unknown delay stays unknown, and the total is then a lower bound. Refer to section 12.

## Semantics

Sections 4, 5 and 7 of the brief define the semantics. Use the result types `Outcome` and `Unknown`. Do not use the result words `open`, `split` and `partly`.

- **Original request.** A `PacketSet` holds pairs of the original request header and the current header. A rewrite changes only the current header.
- **Forwarding choice.** The same packets can go to more than one alternative, for example on equal-cost paths. The engine follows each alternative in a fixed order. The answer shows each path with its own result and a summary over all paths. Section 7 gives the rule.
- **Exit.** A packet that leaves the twin on an edge interface ends in `Exit` with the device and the interface. An edge interface has no link, and its device marks it as an edge (`ExitMark` of `Egress`): a PPPoE interface, an interface that the owner marks, or an interface of a next hop of the default route of the main table whose gateway is outside the twin. The last mark (`ExitMark::DefaultRoute`) holds those gateways, and only the packets whose next hop is one of them exit, so the mark of `::/0` applies only to IPv6 packets; a gateway that is an address of a device of the twin, a next hop with no gateway, a link-local gateway and a WireGuard interface give no mark. `estate.rs` gives the VyOS lowering the addresses of the devices of the twin from the link summaries. An egress with no link on another interface, or with another next hop, is `Unknown`. `Exit` is a terminal verdict like `Deliver` and `Drop`, and it is not `Unknown`. ECMP paths combine by equality and kind, a flood is `Exit` if no copy delivers and a minimum of one copy exits, and an `Exit` branch has no reply. The JSON value of the verdict kind and the outcome kind is `exit`.
- **Match bounds.** An uncertain match set has a definite set and an upper bound. `Unknown` applies only to packets for which the continuations give different outcomes.
- **Knowledge mask and header validity.** An unstated field is not a field with all values. A field exists only where its header is present.
- **Loop.** A loop is a return to the same full state. A second visit to a device is not proof of a loop.
- **Reply header.** An echo request gives an echo reply. TCP flags with only SYN give SYN and ACK. All other TCP flags and ICMP types, the DSCP and the ECN are unstated in the reply.

## QoS and the 3D function view

Section 16 of the brief makes each function QoS aware. Section 17 defines the 3D function view.

- The QoS fields of the packet and the QoS context attributes are part of the core types from step 1, the same as the delay field.
- A function with no declared QoS write passes the marking and the class unchanged.
- Before step 8, lowering changes a QoS stanza into a function that forwards the packets and makes the marking and the class unknown. The trace step names the stanza as not evaluated.
- Functions calculate the marking, the traffic class and the selected queue. Do not simulate queues or rates. For a policer, a shaper or a queue drop, record a rate condition on the branch. With no load data, the branch keeps its outcome. Do not follow the exceed continuation.
- An unhandled QoS stanza does not make a path `Unknown` by itself. The marking becomes unknown, and a later function that reads it uses the match bounds.
- For a query run, the executor emits the events for the 3D view from the trace. The routing step and the delta step emit their own events. Do not put I/O in a function. Do not put render code in the engine.
- The anchor positions and the event stream are deterministic.

## Other design constraints

- Hide the `PacketSet` representation behind the interface in section 4. The representation is an in-house decision diagram engine. OxiDD is a development dependency for tests only, as the oracle for the set operations. Do not make it a dependency of the product.
- The prefix table is in-house, behind a trait.
- Only the `rsim-collect` crate talks to devices. It writes the append-only snapshot store, and the engine reads only the store.
- Lowering changes vendor structures directly into function instances. There is no vendor-neutral config model between them. Refer to section 9.
- The structural parsers contain no vendor knowledge. Classify each stanza as handled, known-irrelevant or unhandled. Do not drop a stanza silently.
- Routing convergence gives one of three results: `Converged`, `MultipleStableOutcomes` or `NoConvergence`. Detect the last two. Do not hide them behind an iteration limit.
- The compiled twin is immutable for each version and is not persisted. The source snapshots are persisted append-only. Rebuild the twin from the sources.
- Batfish is a test aid for oracle comparison only. Do not make it a dependency of the product.
- The product is Rust. `ring` is the only dependency that builds C code, and only `rsim-collect` and `rsim-inventory` use it, for SSH and TLS; `rsim-api` has it through `rsim-inventory`. Do not add another dependency that builds C or C++ code. The rule covers the product: a development dependency of the tests or the benchmarks can build C code, for example `alloca` through `criterion`. Do not turn on `aws-lc-rs` in `russh`, `rustls` or `tokio-rustls`. `blake3` uses its `pure` feature, and `parquet` uses the pure Rust Snappy codec. On Linux, the dependency tree has no `-sys` crate. On macOS, `chrono` adds `core-foundation-sys` and `whoami` of `tokio-postgres` adds `objc2-system-configuration`, bindings to system frameworks.
- `russh` is pinned to one exact version. Turn on the `Legacy` SSH algorithm set only for the devices that need it.
- Only `rsim-collect`, `rsim-inventory` and the server of `rsim-api` use an async runtime. A clock and random bytes are used only in `rsim-collect`, in the writer of `rsim-store`, and for the sign-in: `rsim-inventory` makes the random session tokens, API tokens and password salts, and `rsim-api` uses a monotonic timer for the limit of the request rate. The reader of `rsim-store` uses neither. The database gives the time of each audit record, sign-in event and session, so `rsim-api` and `rsim-inventory` read no wall clock. The engine does not read the inventory database: a twin is built from the snapshot store only.

## Build order

Section 13 of the brief gives the steps, each with a "Done when" condition. Do the steps in sequence. Steps 1, 1b and 2 are complete. Step 1b gives these rules for `rsim-cli` and `rsim-mcp`:

- `rsim-topologies` holds the hand-built topologies. The tests, the benchmarks, `rsim-cli` and `rsim-mcp` use it.
- `rsim-cli` and `rsim-mcp` load a twin and run a path query for one packet with its reply. The product has no built-in topology: a twin comes only from collected data, the newest snapshot of a store, by the owner decision of 2026-11-21. The hand-built topologies of `rsim-topologies` are test fixtures: `rsim-cli` loads them by name only with its feature `test-fixtures`, which only the dev-dependencies of `rsim-cli`, `rsim-mcp` and `rsim-api` turn on, so a test build has them and no binary of the product has them. CI fails when `rsim-topologies` is a normal dependency of `rsim-api`, `rsim-cli` or `rsim-mcp`.
- The JSON output is versioned and deterministic: the same query gives the same bytes.
- `rsim-mcp` uses the stdio transport, has the tools `list_devices`, `path_query`, `set_query` and `explain_step`, and writes nothing. With `--store <data folder>`, the topology `store` is the newest snapshot of that store when a call first names it. A tool call cannot name another store.
- A topology name `store:<data folder>` loads the twin of the newest snapshot of a store through `rsim-ingest`. The store is opened with `Store::open_read`, which writes nothing. It keeps no answer between calls. `explain_step` takes the query, the branch index and the step index, and runs the query again.
- The libraries are `serde` and `serde_json` for JSON and `clap` for the arguments. The MCP protocol code is in-house and has no async runtime.
- The JSON output is version 2. The summary is a list of parts, and each packet value is a set of members with field values. The field names are the names of the Elastic Common Schema where it has one, for example `source.ip`.
