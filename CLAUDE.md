# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository status

Steps 1, 1b and 2 of the build are complete. Step 3 is in progress: collection, the snapshot store, the snapshot view and ingestion. The collection and the ingestion of VyOS, UniFi and NX-OS are complete, with one link join for all vendors. The current batch is EVPN, VXLAN and the anycast gateway in 7 pull requests; pull request 1, the encapsulation in the core, is complete. Then come the HTTP API parts A1 to A3, the Rust TextFSM engine, IOS-XR and IOS-XE. `../rsim-project/roadmap.md` gives the order. The Cargo workspace has 13 crates in `crates/`: `rsim-core`, `rsim-dd`, `rsim-functions`, `rsim-engine`, `rsim-topologies`, `rsim-contract`, `rsim-cli`, `rsim-mcp`, `rsim-api`, `rsim-store`, `rsim-collect`, `rsim-ingest` and `rsim-textfsm`. The other crates of section 3 come with their steps.

The two design documents are in the adjacent folder `../rsim-project/`. This repository is public, so the design documents stay out of it. Do not commit the design documents, real configs or collected state to this repository.

- `../rsim-project/PROJECT_SUMMARY.md` gives the reasoning. Read it first.
- `../rsim-project/BUILD_BRIEF.md` is the build specification. It says what to build.

If the two documents disagree, `BUILD_BRIEF.md` governs.

The hand-built topologies are in the crate `rsim-topologies`, with one module for each topology in `crates/rsim-topologies/src/`. `layer2_site()` is a switched site behind a router for the layer 2 tests; it is not a built-in topology. The tests and the benchmarks of `rsim-engine` use it as a development dependency. `scale_estate(ScaleOpts)` in `rsim-topologies/src/scale.rs` is the generated estate of the scale benchmark, from a fixed pseudo-random sequence; it is not a built-in topology. `rsim-topologies::builtin(name)` gives the twin of a built-in topology.

`leaf_spine()` is a VXLAN fabric of 4 leaves and 2 spines with symmetric routing in one tenant VRF; `rsim-functions/src/tunnel.rs` holds its tunnel ends `VxlanEncap` and `VxlanDecap`.

`rsim-contract` has no engine dependency. It holds the JSON output types, the query echo and error types, the typed arguments of the operations, the brief forms `summary` and `steps`, and the registry of operations in `registry.rs`; `rsim-mcp` makes its tools and their schemas from the registry. `rsim-cli` converts the engine values with the trait `json::FromEngine`. `rsim-contract/src/table.rs` holds the table catalog and the generic selection of rows: filters, sort, pages and the verbs; `rsim-cli/src/tables.rs` gives the rows of each table from a loaded twin, and the MCP tools `list_tables` and `table_query` use them. The table `bgp-sessions` has one row for each BGP peer fact of a store twin, from `Loaded::bgp`. `rsim-contract/src/claim.rs` holds the claim catalog and the rule of the result: one refuted row refutes, one unknown row makes it unknown, and no row is unknown; `rsim-cli/src/claims.rs` gives the evidence rows of each claim, and data that is not collected is unknown. `commands::load` gives a `Loaded` twin with its identity `twin::TwinJson`, and each top-level answer has the field `twin`: `builtin.<topology>` or `snap-<cycle>`, with an empty list of what-if layers. `crates/rsim-cli/tests/schema.rs` checks each stored answer against the schema of its kind and through a round trip, and the flags of `rsim path` and `rsim set` against the registry. `../rsim-project/design/http-api.md` is the API specification.

The stored JSON answers of the CLI tests are in `crates/rsim-cli/tests/golden/`. `<name>.summary.json` and `<name>.steps.json` are the brief forms of `--form summary` and `--form steps`. `leaf-spine-acl.json` and `leaf-spine-no-route.json` are the answers of `FABRIC_QUERIES` in `crates/rsim-cli/tests/cli.rs`. `set-mini-enterprise.json` is the answer of the set query `SET_QUERY` in `crates/rsim-cli/tests/cli.rs`; make it again with `rsim set` and these flags. The CLI test and the MCP stdio test compare their outputs with these files. If an intended change alters the JSON output, make the files again with `rsim path <topology> <flags> --format json`. The flags of each file are in `QUERIES` in `crates/rsim-cli/tests/cli.rs`.

The prefix table in `rsim-core/src/prefix_table.rs` is a path-compressed trie with a read-only walk; `PacketSet::partition_by_prefix` and `PacketSet::partition_by_group` use the walk. `rsim-functions/src/fib.rs` holds the forwarding table `Fib`: the trie, the interned next-hop groups, compact spans and the protocol of each learned route as a column of its entry. A learned route (`RouteKind::Learned` with its `RouteProtocol`) shares the group of a static route with the same next hops, and the `fib` table and the step text name its protocol, for example `bgp`. `RouteLookup` splits a packet set by next-hop group, so a set query gives one branch for each forwarding result. `crates/rsim-core/tests/prefix_oracle.rs` compares the trie and both partitions with a brute-force longest-prefix match. `../rsim-project/design/rib-fib.md` gives the design.

`rsim-core` keeps the packet sets in `packet_set.rs`, the bit table in `bits.rs`, the arenas in `set.rs` and the description of a set as members in `describe.rs`. `crates/rsim-core/tests/explicit_oracle.rs` compares each set operation with an explicit list of packet pairs. Each header bit has 4 levels: the original request, the current header, the work level and the inner level. The encapsulation kinds are GRE, VXLAN, MPLS and WireGuard. A packet has at most one encapsulation: `PacketSet::encapsulate` moves the current header to the inner level and puts the outer header in the current fields, and `PacketSet::decapsulate` brings it back. The inner level is free for a packet with no encapsulation, and `PacketSet::has_free_levels` checks this in the tests. An outer header states each field. The JSON shows the inner header as `inner` of the current header. A path query runs on the set of its packet; the design note gives the rule for an unstated field. The ingress of a query comes from `--ingress` or from the attachment records and edge interfaces of the twin.

The tests of `rsim-dd` turn on the feature `dd-shadow` through a development dependency of the crate on itself. Each public operation then also runs in a plain BDD, and the 2 results must be the same set. A benchmark turns the shadow check off with `Dd::set_shadow(false)`. The OxiDD oracle in `crates/rsim-dd/tests/oracle.rs` compares the results with OxiDD on 3,056 levels. OxiDD is a development dependency only.

`crates/rsim-cli/clippy.toml` and `crates/rsim-mcp/clippy.toml` deny the file write functions and the network socket types. `crates/rsim-api/clippy.toml` denies the file write functions; the server opens only its TCP listener. Only a test helper can allow them.

`rsim-api` is the REST server: `handler.rs` turns one request into one response with no socket, so the tests call it directly; `server.rs` is the HTTP/1.1 layer on `hyper` and `tokio`, with the engine work on worker threads and a limit of parallel queries; `openapi.rs` makes the OpenAPI 3.1 document from its route table and the schemas of `rsim-contract`, and `crates/rsim-api/openapi.json` is the committed copy that a test compares. A query is a resource: `POST /v1/twins/{twin}/queries` gives 303 to `/v1/twins/{twin}/queries/{qid}`, where `qid` holds the canonical query text, or its hash for a long query. Errors are problem objects of RFC 9457. `rsim-cli/src/topology.rs` gives the topology of a twin and the drawing of the paths of an answer, with the overlay edge of a tunnel and its underlay hops; `GET /v1/twins/{twin}/topology` and `GET .../queries/{qid}/topology` serve them. `rsim-mcp` is a library and a binary: `rsim-api` serves its tools at `/mcp`, and the twins of the tools share one cache, so parallel requests do not wait for each other. The brief forms come from the engine answer with no description of the packet sets of the trace steps (`json::brief_json`), so they cost much less than the full form. The server accepts only a loopback listen address, the `Host` of its address and the origins of `--allow-origin`.

`ui/` is the browser UI: TypeScript with Preact, built with Vite, with exact versions in `ui/package.json` and the committed lockfile. `ui/src/theme.ts` holds the colour, type and size tokens of `../rsim-project/design/ui-design-language.md` and sets them as CSS custom properties; `ui/src/app.css` uses only these properties. `ui/src/ladder/layout.ts` and `ui/src/ladder/setLayout.ts` give the lanes, the rows and the cells of the ladder of a path query and of a set query from the full form of an answer, with no drawing code. The drawings are SVG rectangles, lines, circles and text, and the hatch is SVG lines in a clip path. `crates/rsim-api/build.rs` sets the cfg `rsim_ui` when `ui/dist` holds the built files, and `crates/rsim-api/src/ui.rs` embeds them by their fixed names. The server serves them at `/`, `/assets/` and `/fonts/` with a content security policy, and accepts the origin of its own address.

`rsim-store` holds the format of the snapshot store, the writer and the reader. It has no network code. A snapshot manifest lists the devices that the snapshot removes; the reader leaves a removed device out of that snapshot and the snapshots after it until a later snapshot lists the device again, and a checkpoint leaves it out. Each cycle of the collector removes each device of the newest snapshot that is not in the inventory, and the scheduler then takes a device that comes back as new. `rsim-collect` is the only crate that talks to devices. It runs a collection cycle as stages with bounded channels: schedule, fetch, classify and hash, extract, and store. The SSH transport is in `ssh.rs`, the HTTPS transport in `https.rs`, and the credentials and the pins of host keys and certificates in `trust.rs`. `path.rs` holds the route of a device: the proxy and the jump hosts. `tunnel.rs` logs in to each hop of a route, and both transports use it. `cli.rs` holds the text rules of a command line: the cleanup of terminal bytes, the prompt, the banner and the rejection lines of a vendor. The SSH transport has 3 command modes: `exec`, `shell` and `connection`. `../rsim-project/design/vendors.md` gives the rules. The features `ssh` and `https` turn on the transports, and `vyos`, `unifi`, `nxos`, `iosxr` and `iosxe` turn on the sources. The IOS XR source in `iosxr.rs` and the IOS XE source in `iosxe.rs` keep each answer as text; the ages, counters, uptimes and timers are volatile line shapes and word shapes. The IOS XE source reads the MAC table (`mac_table`), the spanning tree (`spanning_tree`), `show vlan brief` (`vlans`), `show standby` (`hsrp_detail`) and `show vrrp` (`vrrp_detail`); `show ip arp` gives the ARP table of the global routing table, and the section `arp_vrfs` gives the ARP table of each VRF: after the other sections, the fetch reads the VRF names from the answer of `show vrf detail` of the same cycle and sends `show ip arp vrf <name>` for each VRF in name order, and the section holds a line `VRF: <name>` before each answer, or the line `VRF: <name> failed` for a failed command. With no answer of the VRFs, `arp_vrfs` is absent, except after a connect error or a timeout of the VRFs or of each command of the VRFs, which `arp_vrfs` takes as its error, so the section keeps its last blob. The NX-OS source is in `nxos.rs`: the JSON answers get one shape, with each `ROW_x` as a list, and a keep list of a section names the fields that the change hash covers. The sections of the VXLAN tunnels, the EVPN MAC routes and the multicast routing have JSON keys that are not confirmed on a device, so they use volatile patterns for their times in place of a keep list. The BGP setting of a router is the field `capture_bgp` of its `Device` (`CaptureBgp`), which `rsim-collect` reads from the env keys `<P>_CAPTURE_BGP` and `<P>_<NAME>_CAPTURE_BGP`: `sessions` reads the session summaries, `all` also reads the neighbour detail (`bgp_neighbors`) and the 3 tables of each IPv4 neighbour of the session answers of the same cycle (`bgp_routes`), and `off` reads no BGP section. `bgp.rs` holds the BGP parts that the sources share. Each BGP section is optional. On VyOS, a BGP answer whose first line starts with `%`, such as the answer of a router with no BGP instance, makes the section absent, and an empty answer is `{}`; an NX-OS switch with no BGP refuses both forms of the sessions, so `bgp_sessions` and `bgp_sessions_default` are absent. IOS XR and IOS XE store the answer of a router with no BGP, a line that starts with `%`, as a fresh section, and `bgp_vrf_sessions` and `bgp_routes` are then fresh and empty; the session reader of `rsim-ingest` takes a summary of only such lines as `NotCaptured`. VyOS reads `show bgp vrf all summary json` (`bgp_sessions`) with a keep list of the AS, the router ID and the state of each neighbour; NX-OS reads `show bgp sessions vrf all | json` (`bgp_sessions`) with volatile patterns for its times and counters, and only when the switch refuses that form `show bgp sessions | json` (`bgp_sessions_default`), which is else absent; IOS XR reads `show bgp summary` and IOS XE `show ip bgp summary` (`bgp_sessions`), and both read the summary of each VRF of the `router bgp` block of the running config of the same cycle in name order (`bgp_vrf_sessions`, with a line `VRF: <name>` before each answer); each number and age of a Cisco summary is a volatile word, so the change hash covers the addresses and the state words. With `all`, IOS XR reads `show bgp neighbors` (`bgp_neighbors`) and `show bgp vrf all neighbors` (`bgp_vrf_neighbors`), IOS XE `show bgp all neighbors` (`bgp_neighbors`), VyOS `show ip bgp vrf all neighbors json` and NX-OS `show bgp vrf all neighbors | json` (`bgp_neighbors`). `bgp_routes` holds a line `NEIGHBOR: <vrf> <address> <direction>` before each Cisco answer, or a JSON object of VRF, address and direction for VyOS and NX-OS; after 2 timeouts in a row, the route commands that are not sent are failed. On VyOS and NX-OS, a session answer that is not JSON makes `bgp_routes` absent, and NX-OS takes the neighbours from the first of `bgp_sessions` and `bgp_sessions_default` whose answer is JSON. A listen range is never a neighbour of a command. The BGP commands are not confirmed on a device, except the VyOS summary and tables on one router. `https` needs `ssh`, because a console can be behind jump hosts. The pipeline tests use the fake transport in `fake.rs` and the synthetic fixtures in `crates/rsim-collect/tests/fixtures/`. The fixtures use only documentation addresses and documentation MAC addresses. The transport tests in `tests/ssh.rs` and `tests/https.rs` run the real transports against servers on 127.0.0.1 in the test process. `tests/support/route.rs` holds the test jump host, which logs each login attempt, and the HTTP CONNECT and SOCKS5 test proxies. The test keys and certificates are made at test time. Do not commit private keys. The scheduler tests and the cycle tests use paused `tokio` time.

`rsim-ingest` reads the snapshot store and gives function instances. It has no network code, no async runtime, no clock and no randomness. `stanza.rs` reads JSON, and indented config text such as a Cisco running config, into a tree of stanzas with the line ranges of the canonical form. ## What the project is

The project is a Rust engine for a network digital twin. The engine compiles configs and collected state into typed network functions that stay in memory. The engine converges the routing internally. To answer reachability questions and policy questions, the engine sends packets or packet sets through the functions. Each answer has a full trace.

The scale target is 10,000+ routers and 50,000+ endpoints.

Section 3 of the brief shows the data flow and the crate layout. The project name is `rsim`, and each crate has the `rsim-` prefix.

## Rules that constrain all code

Section 2 of the brief gives 5 principles. Each principle changes how you write code.

| Principle | Effect on code |
|---|---|
| No confident wrong answers | Return `Unknown` with a reason when the engine cannot be sure. `Unknown` is a valid result. Do not report it as an error. |
| Deterministic | Do not use clocks or randomness. Do not let a result depend on the iteration order of an unordered collection. |
| Provenance everywhere | Each function instance keeps the source spans from which it came. A source span is a file and a line range. |
| Vendor behaviour is data | Put vendor defaults, tie-breakers and implicit rules in vendor behaviour profiles. Do not put them in engine code. |
| Functions written for simulation | Do not add packet buffers, checksums, queues, timers or I/O. |

## Function contract

Section 5 of the brief defines the contract for each function type. The `NetFunction` trait and the `Branch` struct in that section are illustrations. The implementer selects the final form. These invariants are not optional:

- A function accepts a `PacketSet` and returns one or more branches. The branches partition the input. No packet is lost and no packet is duplicated. At a forwarding choice, this rule applies in each alternative. At a flood, it applies in each copy.
- A function declares the context attributes that it needs and the context attributes that it supplies. The compile step of the twin validates the composition. A violation is a build error for that twin.
- A function declares the objects that it reads. These declarations control delta recompilation.
- A function declares the QoS header fields that it reads and writes. The context attribute declarations cover the QoS attributes. Refer to section 16.
- `FlowState` goes into a function and comes out of a function as a value. Do not hide session state or NAT state in a function.
- If part of a function came from an unhandled config stanza, the function returns `Unknown` for the affected packets. If only the match set of a predicate is incompletely known, use the match bounds in item 7 of section 5.

The delay, the alternative of a forwarding choice and the rate condition are part of the core types from step 1. Delay is virtual time. A function does not sleep. An unknown delay stays unknown, and the total is then a lower bound. Refer to section 12.

## Semantics

Sections 4, 5 and 7 of the brief define the semantics. Use the result types `Outcome` and `Unknown`. Do not use the result words `open`, `split` and `partly`.

- **Original request.** A `PacketSet` holds pairs of the original request header and the current header. A rewrite changes only the current header.
- **Forwarding choice.** The same packets can go to more than one alternative, for example on equal-cost paths. The engine follows each alternative in a fixed order. The answer shows each path with its own result and a summary over all paths. Section 7 gives the rule.
- **Exit.** A packet that leaves the twin on an edge interface ends in `Exit` with the device and the interface. An edge interface has no link, and its device marks it as an edge (`ExitMark` of `Egress`): a PPPoE interface, an interface of a next hop of the default route of the main table, or an interface that the owner marks. An egress with no link on another interface is `Unknown`. `Exit` is a terminal verdict like `Deliver` and `Drop`, and it is not `Unknown`. ECMP paths combine by equality and kind, a flood is `Exit` if no copy delivers and a minimum of one copy exits, and an `Exit` branch has no reply. The JSON value of the verdict kind and the outcome kind is `exit`.
- **Match bounds.** An uncertain match set has a definite set and an upper bound. `Unknown` applies only to packets for which the continuations give different outcomes.
- **Knowledge mask and header validity.** An unstated field is not a field with all values. A field exists only where its header is present.
- **Loop.** A loop is a return to the same full state. A second visit to a device is not proof of a loop.
- **Reply header.** An echo request gives an echo reply. TCP flags with only SYN give SYN and ACK. All other TCP flags and ICMP types, the DSCP and the ECN are unstated in the reply.

## QoS and the 3D function view

Section 16 of the brief makes each function QoS aware. Section 17 defines the 3D function view.

- The QoS fields of the packet and the QoS context attributes are part of the core types from step 1, the same as the delay field.
- A function with no declared QoS write passes the marking and the class unchanged.
- Before step 8, lowering changes a QoS stanza into a function that forwards the packets and makes the marking and the class unknown. The trace step names the stanza as not evaluated.
- Functions calculate the marking, the traffic class and the selected queue. Do not simulate queues or rates. For a policer, a shaper or a queue drop, record a rate condition on the branch. With no load data, the branch keeps its outcome. Do not follow the exceed continuation.
- An unhandled QoS stanza does not make a path `Unknown` by itself. The marking becomes unknown, and a later function that reads it uses the match bounds.
- For a query run, the executor emits the events for the 3D view from the trace. The routing step and the delta step emit their own events. Do not put I/O in a function. Do not put render code in the engine.
- The anchor positions and the event stream are deterministic.

## Other design constraints

- Hide the `PacketSet` representation behind the interface in section 4. The representation is an in-house decision diagram engine. OxiDD is a development dependency for tests only, as the oracle for the set operations. Do not make it a dependency of the product.
- The prefix table is in-house, behind a trait.
- Only the `rsim-collect` crate talks to devices. It writes the append-only snapshot store, and the engine reads only the store.
- Lowering changes vendor structures directly into function instances. There is no vendor-neutral config model between them. Refer to section 9.
- The structural parsers contain no vendor knowledge. Classify each stanza as handled, known-irrelevant or unhandled. Do not drop a stanza silently.
- Routing convergence gives one of three results: `Converged`, `MultipleStableOutcomes` or `NoConvergence`. Detect the last two. Do not hide them behind an iteration limit.
- The compiled twin is immutable for each version and is not persisted. The source snapshots are persisted append-only. Rebuild the twin from the sources.
- Batfish is a test aid for oracle comparison only. Do not make it a dependency of the product.
- The product is Rust. `ring` is the only dependency that builds C code, and only `rsim-collect` uses it, for SSH and TLS. Do not add another dependency that builds C or C++ code. The rule covers the product: a development dependency of the tests or the benchmarks can build C code, for example `alloca` through `criterion`. Do not turn on `aws-lc-rs` in `russh`, `rustls` or `tokio-rustls`. `blake3` uses its `pure` feature, and `parquet` uses the pure Rust Snappy codec. On Linux, the dependency tree has no `-sys` crate. On macOS, `chrono` adds `core-foundation-sys`, a binding to a system framework.
- `russh` is pinned to one exact version. Turn on the `Legacy` SSH algorithm set only for the devices that need it.
- Only `rsim-collect` and the server of `rsim-api` use an async runtime. A clock and random bytes are used only in `rsim-collect` and in the writer of `rsim-store`. The reader of `rsim-store` uses neither.

## Build order

Section 13 of the brief gives the steps, each with a "Done when" condition. Do the steps in sequence. Steps 1, 1b and 2 are complete. Step 1b gives these rules for `rsim-cli` and `rsim-mcp`:

- `rsim-topologies` holds the hand-built topologies. The tests, the benchmarks, `rsim-cli` and `rsim-mcp` use it.
- `rsim-cli` and `rsim-mcp` load a built-in topology by name and run a path query for one packet with its reply.
- The JSON output is versioned and deterministic: the same query gives the same bytes.
- `rsim-mcp` uses the stdio transport, has the tools `list_devices`, `path_query`, `set_query` and `explain_step`, and writes nothing. With `--store <data folder>`, the topology `store` is the newest snapshot of that store when a call first names it. A tool call cannot name another store.
- A topology name `store:<data folder>` loads the twin of the newest snapshot of a store through `rsim-ingest`. The store is opened with `Store::open_read`, which writes nothing. It keeps no answer between calls. `explain_step` takes the query, the branch index and the step index, and runs the query again.
- The libraries are `serde` and `serde_json` for JSON and `clap` for the arguments. The MCP protocol code is in-house and has no async runtime.
- The JSON output is version 2. The summary is a list of parts, and each packet value is a set of members with field values. The field names are the names of the Elastic Common Schema where it has one, for example `source.ip`.
